# TOR structure

Use this guideline to read a project Terms of Reference. Do not rewrite a baselined TOR.

## Section skeleton

Keep these sections, in this order:

1. Document Information — 1.1 Document Identification; 1.2 References
2. Project Background and Objectives — 2.1 Background; 2.2 Purpose; 2.3 Objectives
3. Project Scope — 3.1 In Scope; 3.2 Out of Scope; 3.3 High-Level Requirements
4. Deliverables and Acceptance — 4.1 Software Deliverables; 4.2 Documentation Deliverables; 4.3 Acceptance Criteria
5. Constraints and Commitments — 5.1 Technical and Organizational Constraints; 5.2 Timeline and Milestones; 5.3 Responsibilities and Dependencies
6. References

A project may use different category names under 3.3. Do not force category names from any previous project.

## Rules

- Keep objectives, scope, deliverables, and acceptance criteria distinct.
- Do not turn a high-level expectation into an implementation decision.
- Preserve explicit exclusions and constraints.
- Do not assume information that is absent.
- Record whether a detail is explicit, inferred, proposed, or unresolved.
- Structure is stable. Content varies by project.
- A baselined TOR is immutable. Elaborate incomplete statements through elicitation. Do not edit the frozen document.
- A diagram or extra subsection is allowed only when the TOR itself supports it.
